\# NoteMind 团队开发协作规范



\*\*文档版本：\*\* V0.1  

\*\*项目名称：\*\* NoteMind  

\*\*项目类型：\*\* Android 原生 AI 学习与成长平台  

\*\*团队人数：\*\* 4 人  

\*\*开发周期：\*\* 约 1 个月  

\*\*文档状态：\*\* 初稿，待团队确认



\---



\## 一、项目基本介绍



\### 1.1 项目定位



NoteMind 是一款面向大学生的一站式 AI 学习与成长平台。



项目希望通过 AI 技术，将学习资料整理、知识管理、文档创作、学习规划等功能整合到一个 Android App 中，帮助大学生提高学习效率。



\### 1.2 开发原则



1\. 所有成员使用同一个 GitHub 仓库。

2\. 每个人负责相对独立的功能模块。

3\. 每个人在自己的功能分支开发，不直接在 `main` 分支开发。

4\. 功能完成后，通过 Pull Request（PR）合并代码。

5\. `main` 分支必须保持能够正常编译、运行。

6\. 模块之间通过事先约定的接口进行通信。



\---



\## 二、技术选型



以下为推荐方案，最终以团队确认结果为准。



| 部分 | 推荐技术 | 用途 |

|---|---|---|

| Android 语言 | Kotlin | Android 主要开发语言 |

| UI 框架 | Jetpack Compose | 开发 App 页面 |

| 架构模式 | MVVM | 组织页面、业务逻辑和数据 |

| 开发工具 | Android Studio | 编写、调试和运行 App |

| 网络请求 | Retrofit 或 Ktor | 与后端服务器通信 |

| 后端语言 | Python | 后端业务开发 |

| 后端框架 | FastAPI | 提供 HTTP API |

| 数据库 | PostgreSQL | 存储业务数据 |

| 版本管理 | Git + GitHub | 团队代码协作 |



第一版统一使用 Kotlin 开发 Android 业务功能。暂不引入 C++/JNI，后续有高性能计算需求时再考虑。

\## 三、系统整体架构



项目采用 Android 客户端 + 云服务器后端的结构。



\### 3.1 Android 客户端



负责：



\- 用户界面展示

\- 用户操作与交互

\- 文件选择与上传

\- 接收后端返回的数据

\- 展示 AI 处理结果



\### 3.2 后端服务器



部署在华为云 ECS 上，负责：



\- 用户业务接口

\- 笔记和文档业务逻辑

\- 文件处理

\- AI 模型 API 调用

\- 数据库读写

\- 权限验证



\### 3.3 数据存储



负责保存：



\- 用户信息

\- 笔记数据

\- 文件信息

\- 学习任务

\- 其他业务数据



\### 3.4 基本通信流程



```text

Android App

&#x20;    |

&#x20;    | HTTPS 请求

&#x20;    v

FastAPI 后端

&#x20;    |

&#x20;    +---- PostgreSQL 数据库

&#x20;    |

&#x20;    +---- 文件存储

&#x20;    |

&#x20;    +---- 外部 AI 服务

```



Android App 不直接连接数据库，统一通过后端 API 访问数据。

\## 五、团队成员职责分工



团队共 4 人，建议采用模块负责人制度。



| 成员 | 初步职责 | 主要工作 |

|---|---|---|

| 队长 | 项目统筹、笔记模块 | 项目整合、技术规范、笔记核心功能 |

2\. 保证模块能够独立运行或测试。

3\. 按照团队约定的接口开发。

4\. 定期提交代码到 GitHub。

5\. 及时处理代码审核意见。

6\. 配合队长完成最终整合。



\### 5.2 队长职责



1\. 维护项目主分支。

2\. 制定项目技术规范。

3\. 协调模块之间的接口。

4\. 审核成员 Pull Request。

5\. 处理模块整合问题。

6\. 组织最终测试和项目交付。

\## 六、项目代码目录规范



第一版建议使用单个 Android App 工程，按照功能模块划分 package。



```text

NoteMind/

├── app/

│   └── src/main/

│       ├── java/com/notemind/

│       │   ├── common/        # 公共组件、工具类

│       │   ├── navigation/    # 页面导航

│       │   ├── home/          # 首页模块

│       │   ├── notes/         # 笔记模块

│       │   ├── document/      # 文档模块

│       │   ├── user/          # 用户模块

│       │   ├── news/          # 资讯模块

│       │   └── data/          # 公共数据层

│       └── res/               # 图片、图标等资源

│

├── backend/

│   ├── app/

│   ├── tests/

│   ├── requirements.txt

│   └── README.md

│

├── docs/

│   ├── development-rules.md

│   ├── api-documentation.md

│   └── database-design.md
```

\- Android 代码放在 `app` 目录。

\- 所有成员遵守统一目录结构。

\- 未经沟通，不随意修改公共目录和工程配置文件。

\## 七、GitHub 团队协作规范



\### 7.1 仓库管理



团队统一使用以下 GitHub 仓库：



\[NoteMind GitHub 仓库](https://github.com/yukailong147/NoteMind)



建议队长担任仓库管理员，其他成员获得 Write 权限。



\### 7.2 分支管理



采用以下分支结构：



```text

main

├── feature/home

├── feature/notes

├── feature/document

├── feature/user

└── feature/news

```



每个人开发自己的功能分支，不直接在 `main` 上开发。



\### 7.3 日常开发流程



开始工作前，先同步主分支：



```bash

git switch main

git pull origin main

```



然后切换到自己的功能分支：



```bash

git switch feature/notes

```



如果是第一次创建分支：



```bash

git switch -c feature/notes

```



开发完成后：



```bash

git status

git add .

git commit -m "feat: 完成笔记基础功能"

git push -u origin feature/notes

```



后续提交可以使用：



```bash

git push

```



\### 7.4 代码合并流程



统一采用 Pull Request（PR）：



1\. 成员完成自己的功能。

2\. 将功能分支 push 到 GitHub。

3\. 在 GitHub 上创建 Pull Request。

4\. 队长或指定成员审核代码。

5\. 确认没有明显问题后合并到 `main`。

6\. 其他成员拉取最新 `main`，同步代码。



未经沟通，不直接向 `main` 推送开发代码。



\### 7.5 Commit 提交说明



| 类型 | 含义 |

|---|---|

| feat | 新增功能 |

| fix | 修复问题 |

| docs | 修改文档 |

| refactor | 重构代码 |

| style | 格式调整 |

| test | 添加测试 |



例如：



```bash

git commit -m "feat: 添加笔记导入功能"

git commit -m "fix: 修复登录页面错误"

```



\### 7.6 冲突处理



1\. 不要直接删除冲突代码。

2\. 先确认双方修改的目的。

3\. 由相关模块负责人共同决定保留哪些内容。

4\. 解决后重新编译和测试。

5\. 不确定时先联系队长。

\## 八、模块接口协作规范



为了避免不同成员开发的功能无法整合，模块开发前必须约定接口。



例如：



\- 笔记模块需要调用用户模块提供的用户信息。

\- 文档模块需要将提取出的文本交给笔记模块。

\- 首页模块需要调用其他模块提供的功能入口。



\### 8.1 接口约定原则



1\. 模块之间尽量通过明确的接口通信。

2\. 不随意直接修改其他模块的内部代码。

3\. 接口发生变化时，必须通知相关负责人。

4\. 接口文档和代码保持一致。



\### 8.2 后端 API 约定



统一采用 HTTP + JSON 格式。



请求示例：



```http

POST /api/v1/notes

Content-Type: application/json

```



请求内容：



```json

{

&#x20; "title": "高等数学笔记",

&#x20; "content": "函数连续性的相关知识"

}

```



返回内容：



```json

{

&#x20; "code": 200,

&#x20; "message": "success",

&#x20; "data": {

&#x20;   "note\_id": 1,

&#x20;   "title": "高等数学笔记"

&#x20; }

}

```



实际接口需要在开发前由前后端负责人共同确定，并记录在 `docs/api-documentation.md` 中。

\## 九、服务器管理与部署规范



项目统一使用华为云 ECS 作为后端部署服务器。



\### 9.1 服务器用途



\- 部署 FastAPI 后端。

\- 运行 PostgreSQL 数据库。

\- 保存或管理用户上传的学习资料。

\- 调用外部 AI 模型服务。

\- 提供 Android App 所需的业务接口。



\### 9.2 服务器管理原则



1\. 队长负责服务器整体管理。

2\. 服务器账号和密钥不得上传到 GitHub。

3\. 不在代码中直接写入数据库密码或 API 密钥。

4\. 通过环境变量或安全配置文件管理密钥。

5\. 数据库需要定期备份。

6\. 正式部署使用 HTTPS。

7\. 对外开放的端口遵循最小必要原则。



\### 9.3 部署流程



```text

开发成员提交后端代码

&#x20;       ↓

GitHub 合并代码

&#x20;       ↓

服务器拉取稳定版本

&#x20;       ↓

安装或更新依赖

&#x20;       ↓

启动 FastAPI 服务

&#x20;       ↓

测试 API 是否正常

&#x20;       ↓

Android App 连接服务器

```



服务器操作系统、部署工具、域名和 HTTPS 配置待实际服务器开通后确定。

\## 十、项目开发阶段安排



以一个月为参考，建议划分为四个阶段。



\### 第一阶段：项目初始化（第 1—5 天）



\- 确定技术选型。

\- 搭建 Android 工程。

\- 搭建后端工程。

\- 建立 GitHub 团队协作流程。

\- 确定模块接口和目录结构。



\### 第二阶段：模块独立开发（第 6—15 天）



\- 各成员按照分工开发。

\- 定期提交代码。

\- 及时更新接口文档。

\- 每个模块至少完成基础功能。



\### 第三阶段：模块整合（第 16—23 天）



\- 通过 PR 合并功能。

\- 联调 Android 和后端接口。

\- 解决模块之间的兼容问题。

\- 完成主要业务流程。



\### 第四阶段：测试与交付（第 24—30 天）



\- 测试主要功能。

\- 修复 Bug。

\- 优化页面和交互。

\- 完成项目部署。

\- 整理项目文档和演示材料。

\## 十一、待团队确认事项



1\. 最终 Android 技术选型是否采用 Kotlin + Jetpack Compose。

2\. 后端是否采用 Python + FastAPI。

3\. PostgreSQL 是否作为主要数据库。

4\. 四位成员的最终职责分工。

5\. 第一版 MVP 的最终功能范围。

6\. 服务器具体配置、操作系统和管理权限。

7\. 是否使用华为云 OBS 保存用户上传文件。

8\. 各模块具体 API 和数据结构。

9\. 每位成员的 GitHub 账号及仓库权限。

10\. 最终项目展示需要达到的效果。
